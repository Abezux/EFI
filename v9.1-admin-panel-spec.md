# V9.1 — Admin Panel & Takedown Workflow
### Ethiopia News Aggregation Platform

**Scope note:** This document defines V9.1 only — the first of four focused pieces making up V9 (production infrastructure). It builds on V0–V8 (foundation through SEO, plus the V4.1 and V3.1 revisions — all live-verified). It references — but does not repeat — `docs/architecture/platform-architecture.md` (Sections 8, 11, 12). ### 1.2 Functional Scope (architecture doc Sections 8, 12)

**Authentication & authorization**
- Real `users` table (present in the architecture doc's original schema since the first document, unused until now) — email + bcrypt-hashed password, `role` (`admin` | `moderator`).
- No public self-registration — accounts are created via a one-time seed/CLI script you run yourself, not an open signup form. This matches the architecture doc's assumption that admin access is small and trusted, not a public feature.
- Session-based auth: a secure, `httpOnly`, `Secure` cookie on successful login — not `localStorage`/JWT-in-client-storage, which is more exposed to XSS. CSRF protection on all state-changing admin requests.
- Login attempt rate limiting (per-IP and per-account lockout after repeated failures) — this is the first real credentialed login surface in the system and deserves the same care as any production auth.
- `moderator` role can take moderation actions (takedown, restore, resolve review queue); `admin` role additionally manages channels and users. (If this distinction proves unnecessary at your actual team size, it's cheap insurance to have it now rather than retrofitting later — but don't over-build permission granularity beyond this two-role split.)

**Channel management**
- Replaces the current manual `.env`/seed-migration process for adding/removing monitored channels with a real admin UI: list channels, toggle `is_active`, add a new channel (validated against Telegram before being added — reuse the existing channel-resolution logic already proven in the listener).
- Toggling a channel inactive stops the listener from processing new posts from it on its next reconnect/poll cycle — verify this actually takes effect, not just updates a DB flag with no real behavior change.

**Takedown workflow**
- A new `news_events.is_hidden` boolean (separate from the existing `status` field, which tracks clustering state, not moderation state — conflating the two would be a real design mistake).
- Admin/moderator can hide (`is_hidden = true`) or restore an event, with a required reason field.
- A hidden event is **immediately excluded from every public surface** — the API, sitemap, and structured data — with the same discipline already established for `needs_review` exclusion back in V5 (this is the single most safety-critical property in this version, tested explicitly).
- Admin can also detach a single problematic source from an otherwise-valid event (relevant given V3.1's audit tooling surfaced real cases of this) without taking down the whole event.
- Every action — hide, restore, detach, channel toggle — is logged to a new `moderation_actions` table: actor, action type, target, reason, timestamp. This is the audit trail the architecture doc's Section 12 has required since the beginning.

**Manual review queue**
- A page listing current `needs_review` posts (the ones the AI verification step in V4 couldn't confidently resolve) with the candidate event they were compared against, letting a human make the call directly rather than waiting on AI confidence to improve.
- A human resolution is logged the same way an AI resolution is (in `processing_audit`, `model_used` recorded as `human:{email}` rather than a model name) — keeping the existing audit trail consistent rather than creating a second, separate logging path for human decisions.

### 1.3 Why `is_hidden` Is Separate From `status`

`news_events.status` already carries clustering-lifecycle meaning (`active`, `needs_review` per V3/V4). Overloading it with a moderation meaning (e.g., adding a `'taken_down'` value) would mean two very different concerns — "is this event correctly clustered" and "should this event be publicly visible" — sharing one field, which is exactly the kind of conflation that causes bugs later (a future clustering-status change accidentally un-hiding something, or vice versa). A separate boolean keeps them orthogonal and each independently correct.

### 1.4 AGENTS.md Updates

Append a V9.1-specific section:
- Every admin action that changes visible state (hide/restore/detach/channel toggle) must write a `moderation_actions` row in the same transaction — no exceptions, same discipline as `processing_audit` in V4.
- Public-facing queries (API, sitemap, structured data) must filter `is_hidden = false` — any new public query added in a future version that reads `news_events` without this filter is a bug, and this should be checked in review the same way `needs_review` exclusion has been checked since V5.
- Passwords are never logged, never stored in plaintext anywhere (not in logs, not in `moderation_actions`, not in any debug output) — bcrypt hash only, and only in `users.password_hash`.
- Admin session cookies are `httpOnly`, `Secure`, and `SameSite=Strict` — no exceptions for convenience during local dev (use a real local HTTPS setup or accept the friction rather than weakening the cookie flags).

### 1.5 ADR: Admin Authentication Strategy (0014)

- **Context**: the architecture doc anticipated admin/auth needs from the start (Section 8, Section 11's `services/admin/` note) without specifying the mechanism. A decision is needed now that it's actually being built.
- **Decision**: admin functionality lives inside the existing API service (new authenticated route group) and existing Next.js web app (new `/admin` route tree), not a separate standalone service — this is a deliberate scale-appropriate choice (per the architecture doc's "avoid premature complexity" guidance), not a security compromise, since the routes are still fully auth-gated and use a distinct, more-privileged DB role (`efi_admin`) from the public-facing `efi_api` role. Session-based cookie auth over JWT, for the XSS-resistance reasons in 1.2.
- **Consequences**: if the admin surface ever needs to scale independently or be operated by a separate team with different deployment cadence, splitting it into its own service becomes worth revisiting — noted as a real, deferred consideration, not a current need.

### 1.6 Database Changes

New migration `0010_admin_and_moderation.sql`:
```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('admin', 'moderator')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE moderation_actions (
  id BIGSERIAL PRIMARY KEY,
  actor_user_id BIGINT NOT NULL REFERENCES users(id),
  action_type TEXT NOT NULL,   -- 'hide_event' | 'restore_event' | 'detach_source' |
                                -- 'toggle_channel' | 'resolve_needs_review'
  target_type TEXT NOT NULL,   -- 'event' | 'source' | 'channel' | 'raw_post'
  target_id BIGINT NOT NULL,
  reason TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE news_events ADD COLUMN is_hidden BOOLEAN NOT NULL DEFAULT false;
CREATE INDEX idx_news_events_is_hidden ON news_events(is_hidden) WHERE is_hidden = true;

CREATE ROLE efi_admin LOGIN PASSWORD '<never hardcoded, same pattern as efi_api from V5>';
GRANT SELECT, INSERT, UPDATE ON users, moderation_actions, news_events, channels,
  event_sources, raw_posts, processing_audit TO efi_admin;
-- Deliberately no DELETE anywhere, even for admin — takedowns are soft (is_hidden),
-- preserving the audit trail; nothing in this system hard-deletes published data.
```

### 1.7 Security Baseline (this version's central concern)

- This is the first version with real, credentialed access to write operations beyond the pipeline's own service accounts — treat it with the seriousness of any real admin auth system: bcrypt (not a weaker hash), rate-limited login, secure cookies, CSRF tokens on all mutating requests, no verbose error messages that reveal whether an email exists in the system (generic "invalid credentials" on failed login, not "no such user").
- `efi_admin` still has no DELETE privilege anywhere (1.6) — even a compromised or mistaken admin action can't destroy data, only hide it, preserving recoverability.
- Every admin route must independently verify the session/role server-side on every request — never trust a client-side "is logged in" check alone.

### 1.8 Reliability Scope

- If the admin auth system itself has an outage or bug, the **public site must be completely unaffected** — admin routes are fully separate from public routes at the code and DB-role level; a test should confirm the public API keeps working correctly even with admin auth deliberately broken/disabled.
- Channel toggle changes must be picked up by the listener within a reasonable time (its next poll/reconnect cycle) — verify this doesn't require a manual listener restart to take effect, or if it does, document that limitation honestly rather than assuming it "just works."

### 1.9 Testing

- Auth tests: successful login sets a valid session; failed login is rate-limited after repeated attempts; an unauthenticated request to any `/admin` API route is rejected; a `moderator` cannot perform `admin`-only actions (if you keep that distinction).
- **The critical test**: a hidden event does not appear in `/api/v1/events`, `/api/v1/events/{id}`, search, sitemap, or structured data, under any query combination — mirroring V5's `needs_review` leak test exactly, now for `is_hidden`.
- Test confirming every moderation action produces a `moderation_actions` row with the correct actor, action, and target.
- Test confirming a human resolution of a `needs_review` post is logged in `processing_audit` correctly, consistent with how AI resolutions are logged.
- Test confirming the public API remains fully functional with admin routes/auth deliberately failing (1.8).

### 1.10 CI Updates

Extend the existing Go API job and Node web job with the new test files.

### 1.11 Logging

Every admin action logs at the application level too (not just the `moderation_actions` DB row) — actor, action, target, timestamp — matching the correlation-ID discipline used throughout, so admin activity is traceable in the log stream as well as the database.

**Step 5 — Manual `needs_review` resolution**
