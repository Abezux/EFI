# V9.3 — Secrets Hardening & Backups
### Ethiopia News Aggregation Platform

**Scope:** Third of four V9 pieces. Builds on V0–V9.2 (all live-verified). References `docs/architecture/platform-architecture.md` and ADR-0005 (V1's Telegram session storage decision, which explicitly flagged itself for revisit). Two goals: (1) move secrets out of plain `.env` files into a real secrets manager, (2) real Postgres backup/recovery. No processing, clustering, admin, or listener logic changes.

---

## 1. SPEC

### 1.1 Secrets Hardening
- Move all secrets (`TELEGRAM_API_HASH`, `TELEGRAM_SESSION_STRING`, `GEMINI_API_KEY`, DB passwords for `efi_app`/`efi_api`/`efi_admin`) out of `.env` files into a real secrets manager. Pick one reasonable option (e.g., Docker secrets if staying self-hosted, or your hosting platform's built-in secret storage if deploying to a managed platform in V9.4) — the agent proposes a specific choice with reasoning, you confirm before implementing (same pattern as ADR-0007/0008's provider choices).
- Every service reads secrets the same way it does now (environment variables at runtime) — only *where those variables come from* changes. No code should need to know or care whether a value came from `.env` or the secrets manager.
- `.env.example` stays as documentation of what's needed; `.env` itself is no longer where real secrets for anything beyond pure local dev live.
- Rotate the Telegram session string and Gemini key once the new system is in place, confirming rotation doesn't break anything — proves the new system actually works, not just that it exists.

### 1.2 Database Backups
- Automated, scheduled Postgres backups (e.g., daily `pg_dump`, or continuous WAL archiving if the chosen backup tool supports point-in-time recovery — agent proposes, you confirm).
- Backups stored somewhere durable and separate from the primary DB host (not just another file on the same machine).
- A documented, tested **restore procedure** — a backup nobody has ever restored from isn't a real backup. This gets tested for real, once, deliberately.
- Retention policy: keep it simple (e.g., last 7 daily backups) — don't over-engineer at this scale.

### 1.3 ADR-0016
Records: secrets manager choice + reasoning, backup tool/strategy + reasoning, retention policy, and explicitly notes the Telegram session storage decision from ADR-0005 as now superseded.

### 1.4 AGENTS.md Addendum
- No secret may ever be committed, logged, or hardcoded — already true, now enforced by the secrets manager itself rather than just convention.
- Backup/restore scripts live in `infra/` and must be runnable without tribal knowledge — documented steps, not "ask the person who set it up."

### 1.5 Acceptance Criteria
- [ ] All real secrets removed from any committed or locally-sitting `.env` used beyond pure dev.
- [ ] Every service still runs correctly reading secrets from the new source.
- [ ] Telegram session + Gemini key successfully rotated once, confirmed working.
- [ ] A real backup taken, then a real restore performed into a fresh/test database, confirmed data matches — this is the one that actually matters, do it for real.
- [ ] Backup schedule running automatically, not manual-only.
- [ ] ADR-0016 exists; AGENTS.md updated.
- [ ] CI still passes.

## 2. IMPLEMENTATION PLAN (condensed)

1. **ADR-0016**: propose secrets manager + backup strategy, stop for your confirmation before building.
2. **Migrate secrets**: move real values into the chosen manager; update how each service loads them; confirm nothing breaks.
3. **Rotate credentials**: rotate Telegram session + Gemini key through the new system, confirm live pipeline still works.
4. **Backup automation**: scheduled backup job, stored off-host.
5. **Restore drill**: real backup → real restore into a test DB → confirm data integrity. Do this yourself, watch it happen.
6. **Docs + final review** against 1.5.
