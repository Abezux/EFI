# V3.1 — Clustering Window Anchoring & Anti-Drift Safeguards
### Ethiopia News Aggregation Platform (revision to V2/V3, applied before continuing to V8)

**Scope note:** This is a scoped revision to the processor's clustering logic (V2/V3), triggered by real production observation: an event ("Verified Event #1") accumulated 14 sources, of which only 1–2 were actually related. References — but does not repeat — `docs/architecture/platform-architecture.md`, `v2-processing-spec.md`, and `v3-semantic-clustering-spec.md`.

---

## 1. What's Wrong, Precisely

Two compounding root causes:

1. **Centroid drift.** `embedding_centroid` is recalculated as a running average of every attached source (per V3 spec section 1.2). Once a borderline-wrong match attaches, the centroid shifts toward it — making the *next* borderline match easier to accept, since it's now being compared to a drifted average rather than the original story. This compounds with every subsequent attach.
2. **The clustering time window likely slides indefinitely.** V2/V3 specified an ~48-hour candidate window but didn't pin down precisely what it's measured from. If it's implemented relative to `last_updated_at` (which changes every time a source attaches), the window never actually closes — an event can stay "open" forever as long as *something* loosely similar shows up periodically, which is precisely the mechanism that let 14 sources accumulate.

Additionally, this surfaces a real editorial question your instinct correctly identified: **should a news event stay open for updates indefinitely, or should it have a bounded "developing story" window after which new reports become their own event rather than silently merging?** Standard newsroom practice is the latter — bounded developing-story windows, with later related reports becoming separate (optionally cross-referenced) stories rather than being folded into an old one.

## 2. What This Revision Does

**A. Hard-anchor the clustering window to `first_seen_at`, not a sliding window**
- Candidate search (V2/V3's existing 48-hour window logic) changes from "within 48 hours of now" to "within 48 hours of the event's `first_seen_at`." Once that window passes, the event is no longer a clustering candidate for new posts, full stop — a similar post arriving after that becomes its own new event, matching real editorial practice rather than merging indefinitely.
- 48 hours is a reasonable default carried over from the original spec, not re-derived from scratch here — but it's now a real, enforced boundary rather than an ambiguous, effectively-unbounded one.

**B. Anti-drift: compare against the founding post, not just the (possibly-drifted) centroid**
- A new migration adds `news_events.founding_raw_post_id`, set once at event creation, referencing the source that started the event.
- The three-way clustering decision (V3 spec section 1.2) now requires a candidate to be sufficiently similar to **both** the current centroid **and** the founding post's original embedding — not the centroid alone. A post that only matches a drifted average, but not what the story was actually originally about, does not attach.
- This is a deliberately conservative change — it will very likely *reduce* attach rates for genuinely-evolving stories with real topic drift over time, and that's an accepted tradeoff in favor of correctness over volume.

**C. Remediation of existing bad data — reported, not auto-mutated**
- A one-time audit tool re-evaluates every currently-attached source in every existing event against its founding post's embedding using the new anti-drift check, and **reports** (does not automatically detach) any source that fails the check.
- This follows the same pattern already established throughout the project (excerpt length, category list, provider choices) — a decision with real consequences for already-published data gets your explicit review, not a silent automated cleanup. You decide, per flagged case or in bulk, whether to detach a flagged source into its own event, leave it, or investigate further.

**Explicitly not in scope for this revision:** "related coverage" cross-linking between a closed event and a later, genuinely-new-but-related story (a real feature, but a separate one — noted as a future consideration, not built now); any retuning of the underlying similarity thresholds themselves (0.82/0.65 from V3) — worth revisiting once the audit tool shows you the real similarity distribution of your actual bad matches, rather than guessing blindly now.

## 3. Database Changes

New migration `0008_clustering_anti_drift.sql`:
```sql
ALTER TABLE news_events ADD COLUMN founding_raw_post_id BIGINT REFERENCES raw_posts(id);
-- Backfill for existing events: set to the earliest-added_at source in event_sources
-- for each event, via a one-time UPDATE as part of this migration or a follow-up script.
```

## 4. Logic Changes (`services/processor/`)

- `store.go`: event creation now records `founding_raw_post_id`; candidate-fetching query changes from a `last_updated_at`-relative window to a `first_seen_at`-relative hard cutoff.
- `cluster.go`: the attach decision now fetches the founding post's embedding alongside the centroid, and requires both comparisons to pass threshold — not centroid alone.
- New one-time audit command/script (e.g., `services/processor/cmd/audit_clusters/main.go` or similar, run manually, not part of the regular poll loop): for every event, compare each attached source to the founding post, output a report (event id, source id, similarity score, pass/fail) for your review. Read-only — makes no database changes itself.

## 5. Testing

- A test confirming a post arriving after the `first_seen_at`-anchored window closes creates a new event, even if highly similar to an existing (now-closed-to-new-attachments) event.
- A test simulating drift: construct a sequence of attachments where the centroid would drift enough to accept a bad match under the old logic, confirm the founding-post check correctly rejects it under the new logic.
- A test confirming the audit tool correctly flags a known-bad synthetic attachment and correctly does *not* flag a known-good one, without modifying any data.

## 6. Acceptance Criteria

- [ ] Migration `0008_clustering_anti_drift.sql` applied; `founding_raw_post_id` backfilled for existing events.
- [ ] Clustering window verified hard-anchored to `first_seen_at` — a real or constructed test confirms a post outside the window creates a new event.
- [ ] Anti-drift check verified — a constructed drift scenario that would have false-positive-attached under old logic is correctly rejected under new logic.
- [ ] Audit tool run against real production data; you have reviewed its output for "Verified Event #1" and any other flagged events.
- [ ] Based on that review, a decision made and executed (detach flagged sources into their own events, or explicitly leave as-is with reasoning noted) — this is your call, informed by real data, not an automatic action.
- [ ] No change to V4/V4.1 enrichment logic, V5 API, V6/V7 frontend — this revision is scoped to processor clustering only.
