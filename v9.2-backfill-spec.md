# V9.2 — Backfill & Gap Detection
### Ethiopia News Aggregation Platform

**Scope note:** This document defines V9.2 only — the second of four V9 pieces. It builds on V0–V9.1 (foundation through the admin panel — all live-verified). It references — but does not repeat — `docs/architecture/platform-architecture.md` and `v1-ingestion-spec.md` (Section 1.6, which explicitly flagged this exact gap as an accepted-for-now V1 limitation). V9.2's job: close that gap — if the listener is offline (laptop off, crash, deploy restart) when a channel posts, those posts should be caught up on reconnect, not silently lost forever. **Scoped entirely to `services/listener/`** — no changes to processing, clustering, enrichment, the API, or the admin panel.

### 1.2 Functional Scope

- Add `channels.last_synced_message_id` — the highest Telegram message ID successfully ingested (via either live listening or backfill) for that channel. Updated after every successful insert, live or backfilled, so the two paths share one consistent checkpoint.
- **On listener startup** (and on each reconnect after a disconnect — since a disconnect period is exactly when messages get missed), for every active channel: compare the channel's actual latest message ID on Telegram against `last_synced_message_id`. If there's a gap, fetch the missing messages via Telethon's `iter_messages(channel, min_id=last_synced_message_id)` and feed them through the **existing, unchanged** normalization/insert path (`ingest.py`/`db.py` from V1) — this reuses V1's idempotency guarantee, so even if backfill and live-listening ever overlap on the same message, the database constraint prevents a duplicate, not new logic in this version.
- **Backfill is bounded, not unlimited**, for two reasons: respecting Telegram's rate limits, and because a channel that's been dormant for weeks doesn't need its entire history dumped into `raw_posts` — that's not a gap, that's just old content outside the news-relevance window the rest of the system already assumes (the 48-hour clustering window from V2/V3.1). Bound backfill to whichever is smaller: the most recent **N messages** (e.g., 100) or messages within the most recent **48 hours** — matching the system's own existing notion of "recent enough to matter."
- **A brand-new channel** (just added via V9.1's admin panel, no `last_synced_message_id` yet) does **not** trigger a full-history backfill — it starts fresh from whatever's live going forward, same as V1's original behavior. Backfill only applies to catching up a *gap* for a channel that was already being tracked.
- Telegram flood-wait handling: Telethon raises a specific error when hitting rate limits during bulk fetches like `iter_messages` — backfill must catch this, wait the required duration, and resume, not crash or silently abandon the catch-up.

### 1.3 Why Startup/Reconnect-Triggered, Not Continuous Background Polling

A continuously-running background reconciliation job (e.g., checking every channel for gaps every N hours regardless of whether a disconnect happened) would also catch this problem, but it's meaningfully more complexity (a second concurrent process, more Telegram API calls against rate limits, more to reason about) for a failure mode that specifically only happens around disconnects and restarts. Tying backfill to startup/reconnect events directly targets the actual failure mode without adding an always-on process — consistent with the project's running theme of not building infrastructure ahead of a proven need. If a real case surfaces later where gaps happen *without* a visible disconnect (e.g., a silent Telethon failure that doesn't trigger reconnect logic), that's worth revisiting — noted in the ADR as a real, deferred possibility, not dismissed.

### 1.4 AGENTS.md Updates

Append a V9.2-specific section:
- `last_synced_message_id` must be updated by **both** the live-ingestion path and the backfill path, through the same code — do not let two separate implementations of "record what we've synced" drift apart from each other.
- Backfill bounds (message count cap, time window) are configuration values with documented reasoning, matching the pattern already established for clustering thresholds (V3) and stability windows (V4) — not hardcoded magic numbers.
- Backfill must never block the live event loop indefinitely — if a channel's backfill is taking unusually long (e.g., repeated flood-waits), it should log clearly and eventually move on to the next channel / start live listening, not hang the whole listener.

### 1.5 ADR: Backfill Strategy & Bounds (0015)

- **Context**: V1 explicitly deferred this (its own spec, Section 1.6: "V1 does not need to implement gap-detection/backfill... a reasonable V1 limitation to accept explicitly, not silently"). This ADR is where it finally gets addressed and the actual bounds get justified.
- **Decision**: startup/reconnect-triggered backfill (1.3), bounded to the smaller of N=100 messages or 48 hours per channel, reusing V1's existing idempotent insert path rather than introducing new insert logic.
- **Consequences**: a gap longer than 48 hours (e.g., a channel offline for a week) will not be fully backfilled — only the most recent 48 hours of it. This is an accepted, deliberate limitation consistent with the rest of the system's news-recency assumptions, not an oversight; worth stating plainly rather than implying full recovery in all cases.

### 1.7 Reliability Scope

- Flood-wait handling (1.2) — tested explicitly, not just assumed to work because Telethon has some built-in handling.
- If backfill fails entirely for one channel (e.g., persistent API error), it must not prevent other channels from being processed, and must not prevent the live event loop from starting — log the failure clearly and continue; that channel simply stays gapped until the next successful reconnect gives it another chance.
- `last_synced_message_id` updates must happen in the same logical unit as the message insert (matching V1's transactional discipline) — no scenario where a message is inserted but the checkpoint isn't updated (which would cause redundant-but-harmless re-fetching next time, acceptable) or vice versa (checkpoint updated but message not actually inserted, which would cause silent data loss — this direction must not happen).

### 1.8 Testing

- Unit tests for `backfill.py` using a mocked Telethon client: given a channel with a known gap, confirm it fetches exactly the missing range and stops at the bound (message count or time, whichever hits first).
- Idempotency test: simulate a message that both backfill and a live-listener event would both try to insert, confirm only one row ever exists (this should already hold from V1's constraint — this test is about proving V9.2 didn't accidentally break that guarantee, not building new logic).
- Flood-wait test: mock a `FloodWaitError` mid-backfill, confirm the listener waits and resumes rather than crashing.
- A real test: stop the listener, wait a few minutes, post a real message in a real monitored channel, restart the listener, confirm the message is correctly backfilled into `raw_posts` — this is the actual real-world scenario this version exists to fix, worth verifying for real, not just in mocked tests.
